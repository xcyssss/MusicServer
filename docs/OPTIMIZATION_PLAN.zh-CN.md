## 1. 目标与边界

优化目标是让 Windows Tauri APP 启动可靠、播放和操作流畅、故障可理解，并降低后续修改成本。

- 保持 Tauri v2 + WebView2 + 共享 `web/` 的产品架构。
- SQLite 继续作为唯一运行时状态真源；缓存必须可重建，JSON 只用于迁移、备份或兼容输出。
- PowerShell 5.1 / Pester 3.4 是正式验证基线，含非 ASCII 的 PowerShell 文件保持 UTF-8 BOM。
- 保留 worker mutex、SQLite lease/CAS、Provider 有界重试、端口避让、服务所有权及安装版独立运行能力。
- 新增回归使用临时 APP home、临时数据库和测试媒体，不修改正在运行的 Navidrome DB。

## 3. 实施顺序

| 阶段 | 重点 | 主要交付 | 依赖 |
| --- | --- | --- | --- |
| A | 测量与正确性 | 可复用性能基线、数据库连接设置修复、HTTP 输入回归 | 先执行 |
| B | 后端响应速度 | 批量读取、减少重复扫描、隔离慢请求 | A |
| C | 桌面交互与资源使用 | 请求协调、列表渲染、播放器反馈和可访问性 | A；以 B 的接口契约为依据 |
| D | 代码维护与诊断 | 提取重复逻辑、模块边界、统一错误和诊断 | B/C 行为稳定后 |
| E | 安装升级与发布 | runtime 版本识别、升级失败恢复、完整发布验收 | A–D |

每阶段包含多个可独立审查和回退的本地提交。相关步骤完成并通过本地验证后统一推送，减少重复 CI；功能任务随修改补测试，发布相关改动执行真实安装集成验收。

### A. 先建立基线，修复正确性缺口

**A1：建立可复用的测量场景。** 使用隔离 APP home，准备空库、1,000 首和 10,000 首测试元数据，媒体播放只需少量测试音频。记录冷启动到可操作的时间、端点冷/热延迟、每个请求的 sqlite3 启动次数、APP 进程树 CPU/内存、搜索响应时间。固定硬件、数据规模和测量方式，端点每场景至少 30 次，启动至少 5 次；日志留在 `artifacts/`。

**A2：修复数据库连接设置。** 在每次执行 SQL、开始事务之前应用应当逐连接生效的设置；明确初始化与只读连接的契约。先恢复外键设置，单独决定 synchronous 的持久性策略，避免把改变耐久性混进性能修复。验证已有调用是否依赖特殊 PRAGMA，不直接对生产 schema 补外键。

**A3：加固请求读取。** 初始版本的 `music_api.ps1` 按 Content-Length 分配缓冲区后只调用一次 `Read`。改成有上限、检查实际读取长度的读取流程，明确分段到达、提前断开、非法 JSON 和不支持的传输方式如何返回；输入失败必须先于数据库写入。同步审查 UI 代理的请求体转发。

验收：带外键的独立测试 schema 拒绝孤儿记录；有效事务正常提交、失败事务回滚；分段 JSON 可正确解析、超限与不完整请求可控失败且无状态写入。通过 Database / Core / V2 / ApiTransaction / ApiRuntime / WorkerConcurrency 相关回归。

### B. 优化后端响应与数据库访问

**B1：消除推荐冷路径的 N+1。** 在 State 层增加面向推荐响应的批量读取，合并 canonical、wanted、最新反馈的获取。保留返回字段、liked 判定和播放源优先级。以查询/进程次数证明优化，不靠增大缓存 TTL 掩盖冷路径。

**B2：减少重复曲库扫描。** 统一 API 和 UI 对本地文件、Navidrome 条目、稳定 ID 的映射规则。先复用单次请求中的查询结果，再引入可失效的派生缓存；下载完成、删除、手动刷新应能使缓存更新。只有测量证明仍有必要时，再考虑以 SQLite 保存增量索引及对应迁移。

**B3：隔离慢 I/O。** 先做“慢歌词响应/慢音频接收 + 并发 health/控制请求”的复现测试，再引入数量受限的 I/O 执行通道。避免让并发处理器共享可变 `$script:Context`；明确请求上下文、缓存访问、超时、任务取消和 APP 退出时的资源回收。保持状态写入走现有事务和 lease 路径。

验收目标：推荐组装的数据库调用次数不随推荐数量线性增长；对应冷路径 p95 比 A1 降低至少 30%；慢歌词或音频传输期间，health/心跳类小请求 p95 目标低于 500 ms。目标需在 A1 固定数据与机器上确认；同时验证取消下载、快速切歌、Range/416、客户端断开和服务退出。

### C. 优化桌面界面、播放器和前端性能

**C1：统一请求协调。** 提取 fetch 超时、响应校验和错误映射；同类刷新只允许一个有效请求，过期响应不得覆盖较新的结果。保留歌词请求序号并取消已无用的请求。不可见窗口降低数据刷新频率，但保留维持 APP 生命周期需要的心跳；手动刷新能触发明确的数据更新。

**C2：改进列表。** 搜索加入约 150 ms 防抖并正确处理中文输入法组合事件；复用搜索索引和排序结果。检查渲染签名是否包含可见元数据及播放/暂停状态，保留滚动和键盘焦点。先测量现有列表，10,000 条场景不达标时再采用分页或虚拟列表。

**C3：完成播放器状态反馈。** 明确加载、播放、暂停、缓冲、失败和曲目不可用状态；快速切歌保持标题、音频、歌词一致；失败操作提供重试。连接错误文案采用用户能执行的动作，将脚本文件名和 APP home 放到诊断信息中。

**C4：统一布局与可访问性。** 整理颜色/间距/字体变量；检查最小 960×640 窗口、100%/150%/200% 缩放、长歌名、空库和网络失败。补齐按钮可访问名称、可见焦点、键盘操作和状态提示。统计与推荐面板保持信息层级清晰。

验收目标：测试曲库中搜索提交到结果显示 p95 目标低于 250 ms；重复刷新不叠加同类请求；旧响应不恢复已删除条目或覆盖较新状态；无数据变化不重建整个列表。**最终必须在 Tauri APP 中操作并验证**：连续切歌、播放/暂停、拖动进度、歌词、喜欢/取消喜欢、删除、刷新及不同缩放。浏览器测试只作为辅助。

### D. 降低维护成本，改善故障定位

**D1：提取有明确职责的模块。** 前端按 API 客户端、播放器、曲库和歌词分离；PowerShell 先提取 UI/API 重复的曲库映射与歌词规则，再按领域整理 State 的读写入口。保持对外函数、端点与 schema 契约；不将大文件行数本身当作重构理由。

**D2：统一诊断。** 统一错误码、用户提示与可记录的诊断字段，记录请求标识、耗时、超时和 Provider 状态转换。设置日志轮转与容量上限，排除 cookies、凭证和不必要的歌曲私有路径。

**D3：维护测试入口和文档。** `tests/run_suite.ps1` 的失败详情读取方式应与 Pester 3.4 的 `TestResult` 对齐，并固定版本；补一个故意失败的测试夹具证明日志和退出码正确。同步 README、AGENTS checkpoint 和测试索引。

验收：重构前后的关键响应语义一致；新增模块被 runtime 打包脚本完整收集；自动化测试可使用临时数据运行；失败日志可定位到具体测试/端点；PS5.1、BOM、现有 worker 并发回归保持通过。

### E. 提升安装、升级和发布可靠性

**E1：统一构建身份。** 使用构建时生成的版本/内容标识，供 UI、API、Rust 和 smoke 共同使用。禁止嵌入编译机绝对路径。验证旧服务不会因固定字符串相同而被新 APP 错误复用。

**E2：升级失败可恢复。** 当前已完成 runtime 清单校验、跳过相同内容和逐文件临时写入替换；后续补齐跨文件升级失败恢复，明确文件锁定、复制中断、服务仍存活时的处理。只替换应用管理的 runtime 文件，用户数据库、音乐、配置和其他用户文件保持持久化。对 schema 升级准备备份与兼容性方案，再定义可行的回退范围。

**E3：完善启动反馈。** 展示正在准备 runtime、启动服务和失败重试的可理解状态；错误中提供诊断入口。检查启动等待时间、同版本启动的重复文件写入和多实例行为。

**E4：保留并扩充发布门禁。** 继续运行 state、api、真实 Rust/Tauri/NSIS 构建及禁用源码 runtime 的安装 smoke。增加旧版本升级、有锁文件、失败恢复、已有非本 APP 端口占用，以及正常关闭和异常退出后的服务所有权验证。

验收：`cargo fmt --check`、`cargo check --locked`、NSIS 安装包、临时安装、SQLite/runtime staging、当前构建身份、APP 退出服务清理及 artifact 上传全部通过。启动时间和写入量与 A1 对比，已安装 APP 在源码不可用时仍能启动及播放测试音频。

## 4. 分支、验收与回退规则

1. 各阶段使用 `codex/opt-...` 分支，提交前检查并保留无关的本地修改。
2. 当前 CI 的 push 分支过滤仅覆盖 `main` / `review/**`；`codex/**` 应通过 PR 触发检查，或专门修改分支过滤并验证。不能把没有触发的 CI 视为成功。
3. 每个 PR 描述问题、最终行为、相关回归和测量结果；测试门禁或运行规则改变时更新 AGENTS checkpoint。
4. 涉及 UI 的 PR 同时附实际 Tauri APP 验收结果。涉及 runtime 新模块的 PR 验证安装版打包，不只在 checkout 内测试。
5. 代码回退以独立提交为单位；数据库迁移的回退以经过验证的备份/恢复和版本兼容策略为准。
6. 推送后核实对应提交的 GitHub CI。合并仍需要用户明确授权。

## 8. 启动探测边界（2026-09-08，E4 首批）

旧 HTTP 探测使用单次读取超时并一直读到连接关闭，持续慢速发送数据的端口可延长整个探测；读取失败后还可能接受已经收到的标识。现改为连接、写入和读取共用 1.2 秒总期限，最多接收 1 MiB。仅接受读取完成的 HTTP 200 正文标识；响应声明 Content-Length 时必须与实际正文长度一致。错误响应、头部中的标识和超时残片均不能证明服务身份。

服务启动的每组端口重试改为 30 秒实际经过时间，包含探测和休眠。该预算不包含 runtime 文件部署和进程清理；多个候选端口组仍按现有顺序处理，因此不代表整个 APP 启动最多 30 秒。端口避让、服务所有权和 worker lease 规则不变。

本地 Rust 6 项测试通过（5 项探测测试及既有 runtime 文件同步测试）；PS5.1 Tauri 套件 5 项通过。探测测试使用临时 TCP 端口，验证分段、慢速持续发送、未关闭连接、旧标识、错误响应、大小上限及过期预算。完整安装验证以对应 PR 的 desktop-build 结果为准。

本项降低异常端口引起的无界等待，不声称正常启动的约 9 秒耗时进一步下降。当时 E1 构建身份、E2 升级恢复、E3 启动反馈以及 E4 其余场景仍未完成；当前状态以第 5 节为准。

## 9. 内容身份与部署校验阶段（2026-09-08）

- E1：由 `MusicServer.Identity.psm1` 对固定 runtime 脚本和 web 文件的相对名称、SHA-256 摘要生成内容标识。Rust 构建、UI/API 启动和 smoke 共用算法。用户数据、机器路径和生成时间不参与标识。旧服务不会随磁盘文件变化更新自身标识；包中的 SQLite 单独由文件清单校验。
- E2 首批：schema 2 清单含内容标识及完整文件大小/哈希。部署前拒绝不匹配构建、损坏/缺失/多余文件、不安全路径与重解析点。内容未变的文件仍跳过写入；变更文件先写入并同步 APP home 内临时文件，再逐文件重命名替换。
- 实测回归：目录迁移与用户数据不改变标识，runtime 内容改变会产生新标识；HTTP 验证旧进程仍报告旧标识。Rust 验证损坏包不会修改现有 runtime，以及文件锁定时旧内容保持完整、临时文件清理且解锁后可重试。

边界：内容摘要是版本/完整性检查，不是代码签名。逐文件替换不等于整组 runtime 的原子升级：中途失败仍可能留下不同版本文件，下次启动会重新校验安装包并重试。进程崩溃后的临时文件清理、跨文件恢复日志、旧服务仍存活时的升级协调和 schema 备份/回退仍属于 E2 未完成项。E3 启动界面反馈及前端验收继续保留。

阶段本地验证：PS5.1/Pester 3.4 正式套件 190/190，Rust 9/9，NSIS 构建通过；最终 EXE 在隔离 APP home 完成一次当前内容标识与清单部署启动 smoke。单次启动仅用于功能核对，不作为性能对比。阶段提交统一推送后核实完整 CI。
